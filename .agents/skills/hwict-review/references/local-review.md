# 本地提交前审查流程

## 1. 先确定变更范围

记录以下信息：

- 当前分支和目标分支。
- 目标分支与当前分支的共同基点。
- 当前分支相对目标分支的提交范围。
- staged、unstaged 和 untracked 文件。
- 用户明确指定的额外文件或提交。

优先使用 Git 的结构化输出和受限的 `git diff`、`git show`、`git status`。
不要把整个仓库历史当作本次审查范围。

## 2. 再读取相关规则

按变更路径读取最相关的：

- 相关的 `hwict-*` 编码规范 skill（java / vue3 / kotlin / go / mysql / docker）。
- `.agents/notes/implemented/` 中相关架构决策。
- `docs/openapi/` 中受影响的契约、`docs/protocol/`
  中受影响的协议。
- `项目需求与规范.md` 中受影响的约束（安全、权限、软删除等）。
- 受影响模块附近的测试和 fixture。
- 测试代码变更对应的 `hwict-tests` 规则。

不要启动时全文读取所有决策笔记。只读取能解释当前改动边界和决策依据的
Note。

## 3. 追踪直接影响

从变更文件开始，沿真实调用链检查：

- 被修改的声明、调用方和实现方。
- 跨进程、跨语言或跨端边界（Java 后端 ↔ Vue 前端 ↔ Go Agent ↔ Android）。
- OpenAPI 契约、错误码、序列化字段和前端 `src/types/api.d.ts`。
- WebSocket / RabbitMQ 消息契约（`docs/protocol/`）。
- 成功、失败、取消、超时和资源清理路径。
- 直接受影响的测试、验证脚本和文档（OpenAPI、协议、开发日志）。

如果一个结论依赖未修改的调用方，必须说明它如何被本次接口或行为变化触发。

当改动新增或扩大系统能力时，复用边界的追踪步骤与判据按
[统一审查政策](review-policy.md) 的"成熟能力复用审查"一节执行；证据从
`pom.xml`、`package.json`、`go.mod` 和现有适配层取证。Review 默认不访问
网络，证据不足时标记信息缺口，不得猜测依赖能力。

## 4. 验证方式

默认只做静态、只读审查。可以读取用户提供的测试结果，但不得声称运行过
未实际运行的测试。

需要执行验证时，先说明原因和范围，并只运行与当前问题直接相关的验证
（如 `./mvnw test -Dtest=...`、`npm run test -- <file>`、
`npm run openapi:check`）。不要为了 Review 自动启动完整环境、数据库或
长时间构建。

## 5. 交付结论

输出前检查每一条 Finding：

- 是否指向当前变更或其直接影响点。
- 是否有明确触发条件、实际影响和可复现路径。
- 是否说明了为什么属于本次变更的职责范围。
- 是否有对应且足够具体的修改建议。

历史问题和主观偏好只能作为背景，不能作为阻塞项。
